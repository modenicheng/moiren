# ASIO V1 Hardening Implementation Plan

> **For agentic workers:** Use subagent-driven-development or executing-plans to implement this plan task-by-task. Track completed checks here; do not commit or publish without a user request.

**Goal:** Complete capability discovery, truthful diagnostics, bounded control-side recovery, and finite FL Studio ASIO acceptance for the existing stereo ASIO backend.

**Architecture:** Preserve the existing IASIO owner thread, callback rings, ProfessionalBackend and EngineHost. Callbacks publish only atomics; all driver activation, teardown, retry and observation preparation remain outside realtime processing.

**Tech Stack:** Rust 2024, existing Windows COM/IASIO ABI, rtrb, EngineHost, Rust unit/integration and allocation tests.

**Status (2026-10-18):** Implementation and deterministic regressions are complete.
FL capability discovery succeeded, but native IO acceptance failed (zero sustained
callback progress; a later probe hung in stop and was externally terminated).
Do not treat the completed test-execution tasks below as native qualification.

## Global Constraints

- Keep exact requested driver, rate and buffer semantics; never fall back to another API or driver.
- Single ASIO driver, first stereo pair or mono duplication only; arbitrary multichannel is out of scope.
- Native callbacks must not allocate, free, lock, wait, format messages or reopen drivers.
- Distinguish bridge loss, native callback loss, startup silence and driver-reported latency from physical XRUNs or measured round-trip latency.
- Automatic recovery is bounded for unchanged configuration, generation fenced and performed only after old driver teardown.
- Native acceptance may activate only FL Studio ASIO `{188135E1-7171-3434-854F-01A3C71F3DF9}`; use silence, discard capture, finite timeout, leave OS defaults and volume untouched.
- No recording, driver installation, hardware-ASIO qualification claim, commit, push or merge.
