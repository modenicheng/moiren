# Controlled session-mute / Process Loopback feasibility

## Scope and reproduction

The example spawns its own low-amplitude 440 Hz generator in a private WASAPI session, then records statistics from the selected output endpoint's loopback and two independent Process Loopback clients. It cannot select an existing application's PID for modification. Session selection requires the live child PID and an exact single-process session status. Prior volume and mute values are restored and read back before the child is terminated; a Drop guard also retries restoration on an error path.

```powershell
cargo run --locked -p moiren-app -- render --list
cargo run --locked -p moiren-windows-audio --example takeover_probe -- --output '<native 48 kHz stereo f32 endpoint ID>'
```

Each phase lasts 2.5 seconds, including a 0.5 second settling interval. A second newly spawned generator repeats all phases to exercise process/session restart. The probe emits only aggregate samples, peak/RMS, phase labels and restoration values; it stores no PCM or private device/process identity.

The measured endpoint was an already-installed isolated virtual playback endpoint at native 48 kHz stereo. No default device, driver, endpoint volume or existing application session was changed. The probe's raw aggregate result is committed as `2026-10-09-takeover-results.json`.

## Observed results

| Phase | Endpoint RMS | Process capture A RMS | Process capture B RMS |
| --- | ---: | ---: | ---: |
| Baseline | 0.014147 | 0.014139 | 0.014139 |
| Session muted | 0 | 0 | 0 |
| Mute restored | 0.014146 | 0.014138 | 0.014137 |
| Session volume 0.25 | 0.003536 | 0.003534 | 0.003535 |
| Session volume 0 | 0 | 0 | 0 |
| Volume restored | 0.014145 | 0.014138 | 0.014139 |

The second process/session produced the same behavior. Both final restorations read back volume `1.0`, mute `false`, `verified=true`. Both parallel captures continued to operate through the phases. No generator process remained after the experiment returned.

The final probe rejects unexpectedly finished capture workers, fewer than 48,000 finite samples in any stream/phase, and invalid samples. An empty sample set has no RMS value; valid zero-valued samples remain measurable silence. Every phase in the committed final rerun transferred about 192,000 samples per process client, with zero shortfall/XRUN/discontinuity in its measured interval. Transfer diagnostics and restoration values are included in the JSON. The two runs were repeated after the long host generator had stopped so endpoint measurements contained only the experiment's owned child.

In this tested path, session mute and volume suppression also suppress Process Loopback audio. They therefore cannot provide Takeover that silences the original output while retaining an unaffected stream for Moiren. The experiment supports that conclusion for this Windows/endpoint/client combination; it does not establish every endpoint or application behaves identically.

Two simultaneous clients establish underlying API concurrency, rather than an OBS-specific integration result. OBS was not configured or exercised, and third-party application restart, exclusive-mode output and a broad device matrix remain unverified. These results alone do not prove that a custom driver is required: routing to an existing isolated endpoint or another supported mechanism requires its own validation.

API context: [Microsoft Process Loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [session volume controls](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-isimpleaudiovolume). The feasibility conclusion above comes from the recorded measurement, rather than an inference from those documents.
