# 文档体系与写作规则

原则：**规则、决策、证据分开存放；一处一事实源；旧文档不冒充当前验证。**

## 文档类型

| 位置 | 性质 | 谁负责更新 |
|---|---|---|
| [AGENTS.md](../../AGENTS.md) | 顶层规则摘要 + 最高优先级约束 | 规则变化时同步 |
| `docs/development/`（本目录） | 可维护的工程/协作细则 | 规则 owner |
| [FRONTEND.md](../../FRONTEND.md) | UI/设计协作要求（含历史迁移说明） | UI 任务 |
| [README.md](../../README.md) | 项目定位、当前边界、文档索引 | 面向使用者的变化 |
| [docs/TODO.md](../TODO.md) | 已定设计决议 + 当前工作队列 | 决策/排期变化 |
| `docs/designs/NN-*.md` | 编号设计：意图、行为、约束、验收 | 设计变更 |
| `docs/audit/YYYY-MM-DD/` | 只读审计：发现、证据、优先级、整改建议 | 审计轮次 |
| `docs/validation/` | 验收契约/能力边界 | 验收范围变化 |
| `docs/experiments/` | 按日期的实验记录与原始数据 | 实验完成 |
| `docs/designs/screenshots/`、`evidence/` | UI 截图与测量证据 | 对应 UI/性能改动 |
| `docs/superpowers/specs/` | 历史设计快照（冻结） | 不再修改，仅保留 |
| `crates/*/README.md` | 面向使用者的 crate 契约 | crate 行为变化 |
| `docs/development/crates/` | 面向修改者的 crate 指南 | crate 结构/约束变化 |

## 写作规则

- **语言**：正文文档用中文（README、设计、审计、规则）；代码、提交信息、crate 指南保持英文技术写法。术语首次出现给英文原名。
- **状态与日期**：新的设计/审计/验证文档开头写状态、日期和基线提交，例如：
  ```text
  状态：已批准并实施（2026-11-10，基线 main @ de926079）
  ```
  状态可选：草案 / 已批准 / 已实施 / 已废弃 / 部分落地。旧文档不强行改造，但要能看出它是否仍现行。
- **决策可追溯**：设计文档把"用户裁决"逐条列出（编号 + 结论 + 日期）；无法执行或放弃的项写 `resolved-wontfix` 及理由，不静默删除。
- **行为优先**：先写用户可见行为与边界，再写实现；实现细节变化时行为段落保持稳定。
- **可验证**：每个结论尽量给命令、路径、测试名或证据文件；不要写"大概/应该"。
- **不造假**：截图、JSON、命令行输出必须来自当前构建；旧证据要标注日期与基线，不能当作本次验证。
- **链接**：用相对路径链接仓库文件；跨文档引用尽量指向小节标题；定期检查失效链接。
- **不重复**：同一规则只写一处；根 AGENTS 不复制细则，本目录不复制 FRONTEND 的 UI 细节。

## 审计文档

- 一轮审计一个日期目录；`README.md` 放执行摘要、分部分索引、优先级与建议批次。
- 大型审计常用结构：每部分 2 份独立初审（`.a`/`.b`）+ 1 份独立复核（`.verify`），避免单一代理结论污染；小审计可以用"报告 + 整改计划"。
- 审计是**只读**的：不改代码，报告是唯一产出；结论分 proven / high-confidence / unverified，整改建议写成可执行契约。
- 报告随 PR 入库（历史上曾因未入库而丢失）；涉及内网账号、私钥路径等信息必须脱敏。
- 整改按批次小 PR 落地，每条关联报告中的 ID（如 W-1、AS-2）；完成后回填报告状态或在新审计里对账。

## 活文档更新矩阵

| 改动 | 至少更新 |
|---|---|
| 用户可见行为/边界 | `README.md` 对应段落；必要时设计文档状态 |
| 跨 crate 架构/实时约束 | 本目录 `architecture.md`；对应设计文档修订注记 |
| 新增 crate/feature gate/NodeKind | 本目录索引、`repository.md`、`architecture.md`、crate 指南 |
| UI 交互/数据语义 | `FRONTEND.md` 或 `app-ui.md`；设计文档；截图 |
| CI/验证命令 | `verification.md`；`.github` 对应文件 |
| 工作流/协作规则 | `workflow.md` / `collaboration.md`；根 AGENTS 仅在最高优先级规则变化时改 |
| 决策/排期 | `docs/TODO.md`；对应设计文档 |

## 文档生命周期

- `docs/TODO.md` 只记"做什么/为什么"和已定决议，不记实现细节；完成后移出或标 ✅。
- 已落地的计划/跟踪文档不要长期留在 `docs/`；保存到 git 历史即可，当前事实写进设计或 README。
- 过期文档要么更新、要么明确标"历史"，不要删除仍被引用的证据。
- 大型审计/战役结束后做一次文档卫生：失效链接、过期命令、重复段落、与代码矛盾的声明。

## 本地代理记忆（不上库）

仓库 `.gitignore` 把 `.zcode/`、`.superpowers/`、`.tmp/`、`.v2c/`、`.claude/settings.local.json` 等列为"AI Slops"，这些是个人工作记忆，**不提交**：

- zcode 项目记忆：`~/.zcode/cli/memories/projects/<project>/memory/`，`MEMORY.md` 是索引，单篇按 `日期-主题.md` 命名，frontmatter 写 `name`/`description`/`metadata`，正文固定 **Why** / **How to apply**，用 `[[wiki 链接]]` 串联。
- 计划：`.zcode/plans/`（范围、决策、阶段、验证门、风险）。
- SDD 证据：`.superpowers/sdd/`（brief / context / report / review / diff / 命令日志）。
- 维护时机：战役收官、审计定案、踩坑定位、用户拍板之后更新记忆；稳定、可共享的规则再沉淀进本目录。

## 检查清单（提交文档 PR 前）

1. 新规则是否已有 owner 文档？是否重复？
2. 链接是否都能打开（相对路径、锚点）？
3. 命令是否在当前工具链可执行？路径是否存在？
4. 是否写清状态/日期/基线？
5. 是否与代码/CI 现状矛盾？以代码为准修正。
